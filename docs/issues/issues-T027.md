## CRITICAL

### C-01 LMSSetValue Return Value Not Checked ✅ FIXED
**File:** `packages/runtime-player/src/suspend.ts`

`saveSuspendData()` originally returned `void` and called `api.LMSSetValue('cmi.suspend_data', compressed)` without checking the return value. Per the SCORM 1.2 spec, LMSSetValue returns `"true"` on success and `"false"` (or an LMS-specific error string) on failure. Silent failure means learner progress is silently lost — the player would report "saved" via an undefined return but the LMS may have rejected the data.

**Fix:** Changed `saveSuspendData` return type to `boolean`. Check the LMSSetValue result — if it is not `"true"`, log an error and return `false`. Updated `suspendLesson()` in `index.ts` to warn when the save fails.

```typescript
const result = api.LMSSetValue('cmi.suspend_data', compressed)
if (result !== 'true') {
  console.error(
    `[ELearnPlayer] LMSSetValue('cmi.suspend_data') failed — LMS returned: ${result}. Progress may not be saved.`,
  )
  return false
}
return true
```

### C-02 Out-of-Bounds Slide Silently Ignored After Restore ✅ FIXED
**File:** `packages/runtime-player/src/suspend.ts`

`restoreSuspendData()` originally checked `if (payload.slide >= 0 && payload.slide < slideCount)` and skipped the slide assignment when the condition was false — but still returned `true`. This told the caller that the restore succeeded even though the slide was silently discarded. The learner would resume at slide 0 (or wherever state was last set) with question states partially restored, producing an inconsistent player state.

**Fix:** Out-of-bounds slide is now treated as a full restore failure. The function logs a warning and returns `false`, leaving the caller's state object completely unchanged.

```typescript
if (payload.slide < 0 || payload.slide >= slideCount) {
  console.warn(
    `[ELearnPlayer] Suspended slide ${payload.slide} is out of bounds [0, ${slideCount}). Course may have been edited. Ignoring suspend_data.`,
  )
  return false
}
```

## HIGH

### H-01 Negative/Non-Integer Slide Index Accepted in Serialization ✅ FIXED
**File:** `packages/runtime-player/src/suspend.ts`

`serializeSuspend()` had no validation of `state.currentSlide`. A caller passing a fractional or negative slide index (e.g. due to an uninitialized state or arithmetic bug) would produce a payload with an invalid `slide` field. On restore, this would hit the C-02 guard, but the error surface was larger than necessary, and the serialized data would be garbage.

**Fix:** Added an early guard that rejects non-integer or negative slide indices before serialisation begins.

```typescript
if (!Number.isInteger(state.currentSlide) || state.currentSlide < 0) {
  console.error(
    `[ELearnPlayer] Cannot serialize suspend data: invalid currentSlide = ${state.currentSlide}`,
  )
  return null
}
```

### H-02 Mutation of Input State (Pre-Existing Pattern — Not Fixed)
**File:** `packages/runtime-player/src/suspend.ts`

`restoreSuspendData()` mutates the `state` argument in-place (assigns `state.currentSlide`, calls `state.questionStates.clear()`). This violates the project's immutability rule (`coding-style.md`). However, mutation is the pervasive, load-bearing pattern throughout the entire runtime player (`goToSlide`, `handleSubmit`, `scormReport`, etc.). Changing only this function would create an inconsistency; changing the entire player is out of scope for T027.

**Deferred:** Will be addressed in a future refactor task that converts the runtime player to an immutable state model. Function is documented as mutating via JSDoc.

### H-03 Restored Score Values Not Validated — NaN/Division-by-Zero Risk ✅ FIXED
**File:** `packages/runtime-player/src/suspend.ts`

`restoreSuspendData()` originally copied `q.s`, `q.w`, and `q.a` from the decompressed payload directly into `questionStates` without range validation. Corrupt or hand-crafted suspend data could inject `NaN`, `Infinity`, `weight = 0`, or a non-boolean `answered`, which then propagate into SCORM score calculations (score = Σ(score × weight) / Σ(weight)) producing `NaN` or `Infinity` in the final grade.

**Fix:** Values are now clamped in the restore loop:
- `score`: must be a finite number in `[0, 1]`; defaults to `0`
- `weight`: must be a finite number `> 0`; defaults to `100`
- `answered`: must be strictly `=== true`; any other value defaults to `false`

```typescript
const score   = typeof q.s === 'number' && isFinite(q.s) && q.s >= 0 && q.s <= 1 ? q.s : 0
const weight  = typeof q.w === 'number' && isFinite(q.w) && q.w > 0 ? q.w : 100
const answered = q.a === true
```

## MEDIUM (Noted, not blocking)

### M-01 No LMSFinish Error Handling ✅ FIXED

`suspendLesson()` and `finishCourse()` called `api.LMSFinish('')` without checking the return value. An LMS that rejects `LMSFinish` would silently fail.

**Fix (2026-03-22):** Both call sites now capture the return value and emit `console.warn('[ELearnPlayer] LMSFinish returned false — LMS may not have recorded session end.')` when the result is not `'true'`. No recovery action is taken (there is none meaningful at session-end), but the event is now observable in the browser console.

### M-02 Restore Fallback Not Covered by Tests
The `cmi.core.lesson_location` fallback in `init()` (used when `cmi.suspend_data` is absent) is exercised only via integration tests against Moodle, not by the unit test suite.

**Status:** ✅ ACCEPTED — fallback is a single `parseInt` + bounds check; Moodle integration tests (Phase 2.5) will cover it end-to-end. Low risk for v1.
